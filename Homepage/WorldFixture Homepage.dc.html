ONE COMPLETE USE CASE

Find a customer at risk before the renewal call.

Imagine that you are building a product that identifies customers at risk of churn. Start WorldFixture and your app sees Northstar Relay, a synthetic 99-person SaaS company with weeks of activity.

01 · CONNECTPoint your app at local servicesWorldFixture prints the URLs and credentials for Slack, GitHub, Gmail, Stripe, S3, and the other active services.
02 · FIND THE SIGNALSee one risk across systemsSlack discusses Lumen's export failures. GitHub has the engineering issues. Email has the renewal and billing discussion. Stripe has the account and invoice.
03 · STREAM ITLet the world run in real timeEmail arrives, Slack conversations continue, GitHub issues get comments, files appear in S3, and Stripe payments complete through provider events as the clock moves.
04 · REPLAYReset the whole companyReturn every WorldFixture-owned service, event, and clock to the accepted starting state. Run the same E2E test or demo again.
HOW IT WORKS

Use the interfaces your app already knows.

There is no WorldFixture SDK that your application must know about. Mail uses SMTP and IMAP. Storage is S3-compatible. Slack, GitHub, Google, Notion, Stripe, and other services expose local APIs shaped like their providers. Use your normal client and change its base URL.

POINT YOUR APP AT IT

WHEN TO USE IT

Use WorldFixture when your test crosses systems.

USE WORLDFIXTURE
When behavior crosses systems or changes over time.
  • Local integration development
  • E2E tests with shared state and history
  • Repeatable product and sales demos
  • Webhook and scheduled-event flows
  • CI without production accounts
USE A NORMAL MOCK
When one function makes one API call.

A small mock is easier and faster for isolated unit tests. WorldFixture also does not replace final checks against official provider sandboxes. It implements selected provider operations, not every operation.

FAQ

The obvious questions, answered.

WorldFixture is early. These are the boundaries that matter before you try it.

Who is WorldFixture for?

Developers of software that integrates with business services. It is most useful when an application reads several services or reacts to events.

Does it contact real accounts?

No. Included companies, people, customers, credentials, and domains are synthetic. Included domains end in .worldfixture.test.

Is it a collection of response mocks?

No. The local services keep state. Your app and the Workbench use that same state, and the services start from one shared world and clock.

Can I use my normal provider SDK?

Yes, for supported operations. Configure the SDK with the local base URL and credentials that WorldFixture prints.

Can it send events to my app?

Yes. Run the clock in real time or advance it directly. Supported services deliver native provider webhooks, and worlds can send generic HTTP webhooks.

Does it implement every provider API?

No. Support is intentionally explicit and incomplete. Check the provider support index before you depend on an operation.
